## 2. 演进历程：从"能跑"到"能评"

这个项目最有价值的部分不是最初写出来的代码，而是之后的调试和修复过程。下面按时间顺序还原这段迭代。

### 阶段一：核心功能实现

最初按计划完成了核心链路：`PRDAnalyzer`（两阶段 API 调用）→ `Pydantic` 数据模型 → CLI 输出。选型决策如下：

**Tool Use 强制结构化输出**

最初考虑让 AI 返回 JSON 字符串然后解析。改用 function calling 后：
- 输出 100% 符合 schema，Pydantic 直接验证
- 失败快速且清晰：AI 未调用工具 → 立即抛 `ValueError`
- 截断可检测：`finish_reason == "length"` → 明确报错而不是静默损坏

教训：凡是"从 AI 输出提取结构化数据"的场景，优先用 tool use，不要做字符串解析。

**两阶段分析架构**

Phase 1（需求提取）→ Phase 2（任务生成）拆开：每个阶段 prompt 更聚焦，输出质量更高，且两阶段之间可以插入人工审查点（未来可以让 PM 先看完歧义报告再生成任务）。

---

### 阶段二：第一次运行 evaluate.py — 崩溃

写完评测脚本，信心满满地跑第一次：

```
UnicodeEncodeError: 'gbk' codec can't encode character '✓' in position 0
```

原因：Windows 的 GBK 终端编码无法打印 Rich 库的 `✓` 符号。

**修复方案**：
1. `Console(force_terminal=True, highlight=False)` — 绕过 Rich 的编码检测
2. 所有动态内容用 `escape()` 包裹，防止 Rich 标签解析错误
3. 状态指示符改用"达标"/"未达标"纯汉字，完全规避 Unicode 特殊字符

**体会**：开发环境（macOS/Linux）和目标环境（Windows GBK）的差异在终端输出上最容易被忽略，且错误在第一次真实运行才暴露。

---

### 阶段三：崩溃修复后再跑 — 所有分数为零

```
需求覆盖率：30%  歧义检测率：0%
```

AI 输出了 36 条需求、20 条歧义，但评测分数极低。直觉上不对——AI 的输出看起来是合理的。

**排查过程**：手动打印 `_tokenize()` 的输出。

```python
_tokenize("用户可从商品列表页和详情页将商品加入购物车")
# 输出: {"用户可从商品列表页和详情页将商品加入购物车"}  ← 整句话是一个 token！
```

**根本原因**：`_tokenize()` 用标点和空格切分，但中文句子没有词间空格，整句话成为一个 token。两个语义相同、措辞不同的中文句子，token 集合无交集 → F1 = 0 → 全部未匹配。

**修复方案**：中文字符 bigram（滑动窗口，每两个相邻汉字构成一个 token）：

```python
# 修复前：整句作为单 token
{"用户可从商品列表页和详情页将商品加入购物车"}

# 修复后：bigram 分解
{"用户", "户可", "可从", "从商", "商品", "品列", "列表", ...}
```

语义相关的中文句子必然共享大量相邻字对，F1 天然有意义。无需引入 jieba 依赖。

**同步调整**：默认匹配阈值从 0.35 降至 0.25（中文 bigram F1 分布比英文词 F1 偏低）。

---

### 阶段四：Bigram 修复后再跑 — JSON 截断错误

需求覆盖率提升到 ≥80%，但新的报错出现：

```
AI 分析失败：Expecting ',' delimiter: line 1 column 9752 (char 9751)
```

**原因**：`_generate_tasks()` 的 `max_tokens=8192` 不足以容纳 27 个任务的完整 JSON（每个任务含 2 条验收标准 + 描述等多个字段），输出在 char 9751 处被截断，JSON 损坏。

**修复方案**（多管齐下）：
1. `max_tokens` 从 8192 提升到 16000
2. 在 `GENERATE_TASKS_TOOL` schema 中添加 `maxItems: 2`，限制验收标准数量
3. Prompt 增加长度约束：标题 ≤15字、描述 ≤30字、每条标准 ≤20字
4. `_get_tool_args()` 中检测 `finish_reason == "length"` → 抛出明确错误，而不是让 JSON 解析失败时才发现

**体会**：token 截断是隐蔽的失败模式——调用成功（HTTP 200），但数据损坏。解析时才报错，定位成本高。从工程角度，`finish_reason` 检测应该是任何 LLM 调用的标配。

---

### 阶段五：显性歧义检测率偏低 — 精度稀释问题

再次运行评测，需求覆盖率达标，但：

```
显性歧义  │ 60.0% │ >= 80% │ 3 / 5 │ 未达标
```

**排查过程**：

AI 确实检测到了所有 5 条显性歧义，但评测时合并了 `location + issue + clarifying_question` 三个字段作为匹配文本。这导致一条 AI 歧义的 token 集合有 60+ 个 bigram（非常大的分母），而 GT 描述只有 10-15 个 bigram——精度（precision）严重稀释，F1 低于阈值。

**修复方案**：对每条 AI 歧义生成三个候选文本，GT 分别与三者对比，取最高分：

```python
# 候选1：完整拼接（原始做法）
f"{a.location} {a.issue} {a.clarifying_question}"
# 候选2：只用 issue（更精简）
a.issue
# 候选3：只用 clarifying_question（更精简）
a.clarifying_question
```

修复后显性歧义检测率提升到 100%。

**体会**：评测指标本身也是代码，也有 bug。"评测分低"不等于"AI 效果差"，需要区分"AI 没做到"和"评测方法不准确"。这是调试 LLM 系统最容易踩的坑之一。

---

### 阶段六：将 LLM-as-Judge 设为默认

上述所有 token-F1 的修复，根本上都是在用规则逼近语义匹配。既然系统本身就在调用 LLM，不如直接让 LLM 做语义裁判：

```
对每条 GT 条目，把 GT 描述 + AI 全部候选 → 发给 deepseek-v4-flash
让模型回答"YES：候选中有语义等价的条目"或"NO"
```

优点：彻底解决措辞不同但语义相同的匹配问题，准确率远高于 bigram F1。
代价：每次评测多消耗约（需求数 + 歧义数）次 API 调用（约 30-50 次）。

将 `--llm-judge/--no-llm-judge` 的默认值改为开启。Token-F1 模式保留为 `--no-llm-judge` 降级选项（适用于无 API Key 的环境）。

---

### 阶段七：构建 Web 界面

CLI 工具对技术用户友好，但 PM 不会用终端。为了让非技术角色也能使用，增加了 Web 界面：

**技术选型**：FastAPI（后端） + 原生 HTML/CSS/JS（前端，不依赖框架）

选择不依赖 React/Vue 的原因：MVP 阶段交互逻辑简单，引入构建工具链增加维护复杂度而不带来额外价值。单文件 HTML 约 500 行，可直接由 FastAPI 静态服务，部署无额外依赖。

**核心功能**：
- 拖拽上传 PRD，分析结果实时展示（含 30-60s 等待提示）
- 左侧历史文件列表，可切换查看历史报告
- 三标签页报告：需求（按类型分组）/ 歧义（含澄清问题高亮）/ 任务（含验收清单）
- 深色/浅色主题（localStorage 持久化）
- 一键导出 JSON 和 Markdown

---

### 阶段八：引入真实 PRD 夹具

测试夹具全部自己编写存在明显局限：人工撰写的 PRD 结构规整、歧义刻意，与真实 PRD 的"自然混乱"不同。

从真实开源项目（TokenRouter，一个 LLM API 网关）获取了真实 PRD，人工标注 ground truth：
- 22 条需求（15 功能 + 7 非功能）
- 8 条歧义（2 显性 + 6 隐性）

真实 PRD 的特点：
- 存在隐式需求（User Story 中提到但没有独立章节）
- 歧义藏在技术决策中（如"50个子Agent测试工程师"语义不明）
- 存在 Out of Scope 章节需要负向判断（AI 不应把不在范围内的内容当需求）

## 3. 做对了什么

### 3.1 Tool Use + 两阶段架构（最关键决策）

强制结构化输出和阶段拆分是整个系统质量的基础。两个决策互相增强：
- Tool Use 保证了每个阶段的输出是可编程处理的结构
- 两阶段保证了每个 Tool 的 schema 可以保持简单、专注

### 3.2 "评测分低 ≠ AI 效果差"的意识

这次迭代中最重要的认知转变。当评测分数异常（如歧义检测率 0%）时，第一反应不是去改 prompt，而是先排查评测方法本身。实际上三次"效果差"都是评测代码的问题：tokenizer、精度稀释、Unicode 崩溃。

### 3.3 分层防御 JSON 截断

四个层次同时加固（max_tokens + schema 约束 + prompt 长度限制 + finish_reason 检测），单一修复容易反复，多层防御更稳定。

### 3.4 Ground Truth 驱动开发

有了可量化的 ground truth 和评测脚本，每次修改后可以立即知道指标变化方向。这是调试 LLM 系统的基础设施，比反复人工阅读 AI 输出效率高得多。

## 4. 做得不够好的地方

### 4.1 先写代码后写 GT（顺序颠倒）

ground truth 和评测框架在核心功能完成后才写。理想的顺序是：先定义"什么算成功"（GT + 评测指标），再写代码，最后调优——即测试驱动。这样可以避免后期才发现"我无法自动化验证我的目标"。

### 4.2 token 截断问题应该更早被发现

`max_tokens=8192` 对 20+ 任务的 JSON 明显不够，但直到实际运行才报错。更好的做法是：在 prompt 设计阶段估算最坏情况的 token 消耗，并在集成测试中用"复杂 PRD"做冒烟测试。

### 4.3 Web 界面未进行端到端真实测试

前端功能在浏览器中手动验证了核心路径，但未进行系统性的边界测试：
- 超大 PRD 文件上传（> 1MB）
- 分析失败时的错误展示
- 多文件并发上传（内存存储无锁）

### 4.4 内存存储是生产阶段的隐患

当前 `_store: dict` 在进程重启后清空，多实例部署时各自独立。对 MVP Demo 够用，但文档中应明确标注这一限制，避免使用者误解为持久化方案。

## 5. 如果再做一次，会改变什么

### 最高优先级的改变

**先定义评测，再写功能**

```
Day 1: 写 fixtures/complex_prd_ground_truth.json
       定义评测指标和阈值
       写 evaluate.py 骨架（即使 AI 还没接入）
Day 2: 实现 PRDAnalyzer，每次修改后跑评测
Day 3: 调优 prompt + schema，看指标变化
```

这样就不会出现"功能写完才发现评测方法有 bug"的情况。

**从第一天加入 finish_reason 检测**

```python
if response.choices[0].finish_reason == "length":
    raise ValueError("Response truncated — increase max_tokens or reduce output verbosity")
```

这是任何 LLM API 调用的标配防御，成本极低，收益极高。

**加入 retry 逻辑**

```python
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(3), wait=wait_exponential(min=1, max=10))
def _call_api(...):
    ...
```

生产环境必需，应从 Day 1 就加入，而不是 MVP 完成后再补。

### 时间分配的调整

```
实际分配（回顾）：
  核心功能实现：~40%
```

## 6. 关键学习

### 关于 AI Native 产品设计

> "AI 介入点的设计比 AI 本身更重要。"

这次选择了"PRD → 任务"这个环节，是因为：输入边界清晰（一份文档）、输出定义明确（结构化任务）、人工验证容易（Tech Lead 有判断力）。

如果选择了"帮 PM 写 PRD"这个环节，输入输出都更模糊，AI 介入效果会差得多。**找到合适的介入点比 AI 能力更决定成败**。

### 关于调试 LLM 系统

LLM 系统的调试不同于普通软件：
- **失败可能是静默的**：HTTP 200，但输出被截断或语义偏移
- **评测本身也可能有 bug**：分数低不一定是 AI 的问题
- **关联性不等于因果性**：改了 prompt 后分数提升，不代表 prompt 是根因

最有用的调试工具：可量化的 ground truth + 快速的评测脚本。比人工阅读 AI 输出效率高 10 倍。

### 关于 Tool Schema 设计

Tool use 不只是"结构化输出"的技巧，更是**人机接口的契约定义**。Schema 设计的质量直接影响 AI 输出的质量和系统的可维护性：
- 字段命名影响 AI 对语义的理解（`clarifying_question` 比 `question` 更明确）
- `enum` 约束可以消灭大量的"aliases"问题（AI 有时输出 "critical" 代替 "high"）
- `maxItems` 可以控制输出长度，防止截断

### 关于中文 NLP 的特殊性

中文文本处理有其特殊性，不能直接套用英文经验：
- **无词间空格**：按空格分词完全失效，整句话成为单 token
- **Bigram 是实用的基线**：无需分词库，共享 bigram 的中文句子在语义上通常相关
- **LLM-as-Judge 是最终答案**：bigram 解决了"完全没有交集"的问题，但语义匹配最终还是需要语言模型来做
